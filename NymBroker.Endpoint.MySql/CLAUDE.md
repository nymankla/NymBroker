# NymBroker.Endpoint.MySql

`MySqlEndPoint` — a lease-based queue table for MySQL 8.0+ / MariaDB 10.6+ (the first versions with `SKIP LOCKED`; `JSON_TABLE` needs MySQL 8.0.4+). Same lifecycle, leases, retry/`Failed` handling and logging as the PostgreSQL and SQL Server endpoints (private `Listener : LeasedQueueListener`). Driver: **MySqlConnector** (MIT, truly async) — not Oracle's `MySql.Data`. No Dapper. SQL in `MySqlQueueSql`. Only MySQL 8.4 is tested (`scripts/setup-mysql.ps1`); MariaDB is documented, not tested.

- **Claim = two round trips in one transaction** (MySQL has no `UPDATE … RETURNING`):
  1. `FinalizeAndLock`: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED; START TRANSACTION;` → finalize batch N → reset expired leases to Pending → `SELECT queue_id … WHERE status = 0 ORDER BY queue_id LIMIT @batchSize FOR UPDATE SKIP LOCKED`.
  2. `Claim`: `UPDATE … WHERE queue_id IN (<ids>)` + `SELECT` the rows + `COMMIT`. The ids are inlined (BIGINTs read from the table).
  No ids → just `COMMIT`. On any exception the endpoint sends `ROLLBACK` before the connection goes back to the pool — otherwise the open transaction would keep its row locks until the pooled connection is reused.
- **READ COMMITTED** so the locking read takes no gap locks (under REPEATABLE READ a claim that reaches the end of the index range would block concurrent `INSERT`s until commit).
- **Index**: MySQL has no partial/filtered index, and a generated column cannot reference the `AUTO_INCREMENT` key, so the claim index is `(status, queue_id)`. The claim only reads `status = 0` (an index range in id order, no filesort — `Claim_ReadsOnlyThePendingRangeOfTheStatusIndex` checks the plan). Expired leases are not claimed directly: the reset `UPDATE … WHERE status = 1 AND locked_until_utc <= now` (the small `status = 1` range) turns them back into Pending, keeping `attempt_count`; a late finalize from their old owner is a no-op because the guard needs `status = InProgress`.
- **Measured** (scratch harness, 5 000-message backlog, 200-byte payloads, local container): `BatchSize` 10 ≈ 1 400–1 700 msg/s, `BatchSize` 50 ≈ 5 800–6 400 msg/s, **the same with 300 000 Completed rows in the table** — finished rows don't slow claiming.
- **Finalize**: one `UPDATE … JOIN JSON_TABLE(@items …)` for mixed outcomes; with a realistic table the optimizer drives from `JSON_TABLE` and seeks each row by primary key (`Finalize_FindsRowsByPrimaryKey`). Guard: `status = InProgress AND attempt_count = source.attempt`. `error … NULL ON EMPTY` keeps a JSON `null` error as SQL `NULL`.
- **Schema**: InnoDB, clustered `queue_id BIGINT AUTO_INCREMENT`; `message_id BINARY(16)` (written as `Guid.ToByteArray()`, read as bytes — independent of MySqlConnector's `GuidFormat`), `payload LONGBLOB` (bytes unchanged), `last_error MEDIUMTEXT` (an exception text can exceed `TEXT`'s 64 KB, and strict mode would then fail the finalize forever), `DATETIME(6)` times from `UTC_TIMESTAMP(6)`. `CREATE TABLE IF NOT EXISTS` with the index inline (MySQL has no `CREATE INDEX IF NOT EXISTS`). `TableName` is `table` or `db.table`, each part `^[A-Za-z_][A-Za-z0-9_$]*$`, backtick-quoted; validated at registration and in the constructor.
- **Inserts**: one autocommit `INSERT` per `PostAsync`; `PostBatchAsync` is one multi-row `INSERT` (atomic; AUTO_INCREMENT values follow the VALUES order).
- **Connections**: one pooled `MySqlConnection` per operation (not thread-safe). Polls on a timer when idle (no LISTEN/NOTIFY).
- JSON for `@items` uses reflection-based `System.Text.Json`, like the SQL Server and Postgres endpoints.

**Deferred messages** wait in `<table>_deferred` with an index on the due time, never in the queue table: the claim index and plan don't change, however many wait, and older package versions never deliver them early. `LockDue` + `PromoteDue` move them in a transaction of their own (two round trips, `SKIP LOCKED`, `ROLLBACK` on failure); `LeasedQueueListener` decides when.

**Retention**: `DeleteFinishedAsync` runs `DeleteCompleted` / `DeleteFailed`: one `DELETE … LIMIT @batchSize` at READ COMMITTED (no gap locks). Completed rows are found through `ix_completed_at (completed_at_utc)`, deliberately without `status`, so a claim's status changes don't write to it. Failed rows use the `status = 3` range of `ix_status_queue`. MySQL has no `CREATE INDEX IF NOT EXISTS`, so `CreateSchemaAsync` checks with `SHOW INDEX` and `ALTER TABLE`s an existing table, ignoring `DuplicateKeyName` when another instance got there first.

Read-only queue inspection is implemented by `MySqlEndPoint` through `IQueueInspector`. Counts are one statement/snapshot; pages are oldest-first keyset queries using `queue_id` for active states and `(failed_at_utc, queue_id)` / `(deliver_at_utc, deferred_id)` for failed/deferred states. The inspector does not claim messages; Completed rows are count-only. Integration tests: `MySqlEndPointTests` and `MySqlQueueInspectorTests` (`NYMBROKER_MYSQL_CS`, `./scripts/setup-mysql.ps1`), unique tables per test. The idempotency store is a separate package (`NymBroker.Idempotency.MySql`): `INSERT … ON DUPLICATE KEY UPDATE` that takes over only an expired row and stamps it with a random `claim_token`; the result is decided by reading the token back (`<=>`, null-safe), never by the affected-rows count, which depends on the connection's `UseAffectedRows` setting. Shared parts (argument checks, cursor format, reading the counts, the page loop) are in `shared/Inspection` ([shared/README.md](../shared/README.md)).
